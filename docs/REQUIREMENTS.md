# 요구사항 정의

CampusPlan의 기능 요구사항과 범위를 정리한 문서입니다. 프로젝트 제안서(로컬 보관, 저장소에 올리지 않음)의 내용을 기준으로 하고, 이후 구현된 DB 설계와 달라진 부분은 [계획과 현재 설계의 차이](#5-계획과-현재-설계의-차이)에 따로 표시했습니다.

- 이 문서의 기능 번호(FR-xx, NFR-xx)는 이슈와 API 명세에서 참조할 수 있게 붙인 것입니다.
- 구현 진행 상태는 이 문서에 적지 않습니다. 진행 상태는 [루트 README](../README.md)와 `CLAUDE.md`를 확인합니다.

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 서비스명 | CampusPlan (캠퍼스플랜) |
| 한 줄 정의 | 대학 학업 일정과 졸업 준비 현황을 통합 관리하는 학생용 대시보드 |
| 주요 사용자 | 한서대학교 학생 |
| 개발 목표 | 학생·과목·학기·수강 이력·봉사활동 데이터를 일관된 구조로 관리하고, 학점 집계·봉사시간 일괄 승인·졸업요건 진단을 DB의 Trigger·Procedure·View로 처리 |
| 개발 형태 | 데이터베이스 캡스톤디자인, 2인 팀 |

## 2. 기능 요구사항

우선순위는 제안서 기준입니다.

| 번호 | 기능 영역 | 요구사항 | DB 활용 | 우선순위 |
| --- | --- | --- | --- | --- |
| FR-01 | 학생 관리 | 학생 기본 정보 등록·조회·수정, 대상 학생 기준 데이터 연결 | 기본 테이블 | 높음 |
| FR-02 | 과목·학기 관리 | 과목 정보 조회, 학기 생성 및 학기별 과목 구성 | 기본 테이블 | 높음 |
| FR-03 | 시간표 | 요일·교시·강의실을 기준으로 학기별 주간 시간표 표시 (담당교수는 현재 DB에 저장하지 않음) | JOIN 조회 | 높음 |
| FR-04 | 학점 현황 | 성적 입력·수정 시 이수 완료 여부를 자동 판별하고 누적·전공·교양 학점을 집계 | Trigger, View | 높음 |
| FR-05 | 봉사시간 관리 | 봉사활동 내역 등록, 대기 상태 내역의 일괄 승인, 승인된 시간 합산 | Procedure, View | 중간 |
| FR-06 | 졸업요건 진단 | 학점 기준, 필수과목 이수 여부, 봉사시간 기준 대비 부족 항목을 기준별로 표시 | View | 높음 |
| FR-07 | 대시보드 | 이번 주 일정, 학점 요약, 졸업 진단 결과 요약 표시 | View 조회 | 중간 |

### 기능별 상세

- **FR-04 학점 현황**: 성적(`grade`)이 `A+`~`D`, `P`이면 이수 완료, `F`, `NP`이거나 성적이 없으면 미이수로 판정합니다. 같은 과목을 재수강하면 학점은 과목당 한 번만 인정합니다. 성적 척도와 이수 기준은 임시 가정입니다.
- **FR-05 봉사시간 관리**: 봉사 내역은 `대기`, `승인`, `반려` 상태를 가집니다. 승인된 시간만 누적 봉사시간에 반영합니다. CSV 업로드는 후순위 확장 기능입니다.
- **FR-06 졸업요건 진단**: 학생에게 적용되는 졸업 규칙별로 현재 값, 기준 값, 충족 여부를 보여줍니다. 공식 자료로 확인되지 않은 규칙(`is_verified = FALSE`)은 화면에서 구분해 표시해야 합니다.

## 3. 화면 요구사항

제안서의 프론트엔드 구현 단계 기준 화면 목록입니다.

| 화면 | 관련 기능 | 보여줄 내용 |
| --- | --- | --- |
| 대시보드 | FR-07 | 이번 주 일정, 학점 요약, 졸업 진단 요약 |
| 시간표 | FR-03 | 학기별 주간 시간표 |
| 학점/성적 | FR-04 | 수강 이력, 성적, 이수 여부, 누적·전공·교양 학점 |
| 봉사시간 | FR-05 | 봉사활동 내역, 승인 상태, 승인된 누적 시간 |
| 졸업요건 진단 | FR-06 | 기준별 현재 값과 기준 값, 충족 여부 |

학생·과목·학기 관리(FR-01, FR-02)의 입력 화면 구성은 아직 정해지지 않았습니다.

## 4. 비기능 요구사항

| 번호 | 요구사항 |
| --- | --- |
| NFR-01 | 처음 접속했을 때 주요 상태를 빠르게 이해할 수 있는 대시보드 구조를 사용한다. |
| NFR-02 | 화면과 API의 역할을 분리해 프론트엔드와 백엔드를 독립적으로 수정할 수 있게 한다. |
| NFR-03 | 학점 계산과 일괄 승인 로직은 DB의 Trigger·Procedure로 처리해 정합성을 보장한다. 같은 규칙을 백엔드나 프론트엔드에 다시 구현하지 않는다. |
| NFR-04 | 시연을 위해 테스트용 학생과 샘플 데이터를 준비하고, 실제 학사 데이터와 구분해 관리한다. |
| NFR-05 | 입력값을 검증하고 SQL은 파라미터 바인딩을 사용한다. |

## 5. 계획과 현재 설계의 차이

제안서의 부록 SQL은 설계 초안이었고, 구현 과정에서 아래와 같이 바뀌었습니다. 현재 기준은 `database/`의 SQL 파일입니다.

| 제안서 초안 | 현재 설계 |
| --- | --- |
| `Student.total_credits`, `total_volunteer_hours` 컬럼에 누적값 저장 | 누적값을 저장하지 않고 View(`CreditSummary`, `VolunteerSummary`)로 계산 |
| 트리거 `trg_before/after_enrollment_update`가 `Student.total_credits` 갱신 | 트리거 `trg_enrollment_insert`, `trg_enrollment_update`가 `completed`만 판정 |
| 프로시저 `sp_approve_volunteer_hours` | `ApproveVolunteer`(내역 1건), `ApproveAllPendingVolunteer`(학생 단위 일괄) |
| 뷰 `v_graduation_status` (PASS/INCOMPLETE 한 행) | 뷰 `GraduationCheck` (학생 × 졸업 규칙, 규칙별 `is_met`) |
| `Volunteer` 테이블, 상태 `PENDING`/`APPROVED` | `VolunteerRecord` 테이블, 상태 `대기`/`승인`/`반려` |
| `Graduation_Rule`에 학과별 기준 컬럼(총·전공·봉사 등) | `GraduationRule`을 규칙 종류별 행으로 저장(학부·학과·입학년도 구간으로 적용) |
| `Student.department`(문자열) | `Student.department_id` → `Department`(입학년도별 학부·학과) |
| 7개 테이블 | `Department`가 추가된 8개 테이블 |
| `Schedule` 시간표 | 같은 학생·학기의 요일·교시 충돌을 막는 트리거 `trg_schedule_conflict` 추가 |

## 6. 데이터 요구사항

- **실제 자료**: `data_sources/official/`의 공식 자료(졸업학점표, 학과 졸업자격 규정, 2026학년도 2학기 강의시간표)에서 만든 값만 기준 데이터(`05_seed_master.sql`)에 넣는다.
- **테스트 데이터**: 실제 자료로 확인되지 않는 값(학생, 수강 이력, 봉사 내역, 시연용 졸업 규칙)은 합성 데이터(`06_seed_test.sql`)로 분리하고 실제 데이터와 섞지 않는다.
- **확인 상태**: 졸업 학점 기준은 공식 졸업학점표를 반영했다. 봉사 시간 기준과 필수과목 규칙은 공식 근거가 확인되지 않아 아직 기준 데이터에 없다.

## 7. 범위

| 포함 | 제외 또는 제한 |
| --- | --- |
| 확인 가능한 과목 데이터의 정제 및 일괄 입력 | 샘플 데이터 확인 전 과목 내용·과목 수의 확정 |
| 학생 1인 기준의 학업 관리와 진단 | 다수 사용자 운영, 복잡한 관리자 권한, 멀티테넌시 |
| Trigger, Procedure, View를 이용한 DB 수준 자동 집계와 일괄 처리 | 실시간 성적 자동 수집, 외부 대학 시스템 연동 |
| 테스트 데이터와 CSV 샘플로 부족한 정보(봉사시간 등) 보완 | 상용 서비스 수준의 인증, 개인정보 보호 체계, 배포 자동화 |
| 기본적인 입력 검증과 시연 환경 보안 | CSV 업로드 기능은 일정에 따라 후순위 확장 |

## 8. 미확정 사항

| 항목 | 내용 |
| --- | --- |
| 인증 방식 | 정해지지 않았다. 학생을 식별하는 방식은 API 명세에서 가정으로 적는다. |
| 배포 방식 | 정해지지 않았다. |
| 과제 관리 | 제안서 배경 설명에는 "시간표와 과제 관리"가 나오지만 기능 요구사항 표에는 없다. 범위에 포함할지 확인이 필요하다. |
| 교양 세부 졸업 기준 | 교양필수·교양선택 세부 최소학점, 교양선택 핵심역량 영역 조건은 아직 규칙으로 구현하지 않았다. |
| 봉사 시간 기준 | 제안서와 조사 자료의 30시간은 공식 근거가 확인되지 않았다. |
| 필수 과목 규칙 | 항공소프트웨어공학과의 `항공소프트웨어프로젝트1·2`는 공식 규정에 있으나, 조건부 필수와 인턴 예외를 처리하는 방식이 정해지지 않았다. |
| 성적 척도·이수 기준·학기 상태값 | 임시 가정이다. |
