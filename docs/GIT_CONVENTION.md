# Git 커밋 컨벤션

팀원이 커밋 목적을 빠르게 파악하고 변경 이력을 쉽게 추적할 수 있도록 아래 규칙을 따릅니다.

## 메시지 형식

```text
<type>: <한글로 작성한 변경 내용>
```

유형은 영어 소문자로 작성하고, 설명은 한글로 간결하게 작성합니다.

```text
feat: 로그인 화면 추가
```

콜론 앞뒤에는 공백을 넣지 않습니다. 오타 수정은 다음과 같이 작성합니다.

```text
chore: 오타 수정
```

## 커밋 유형

| 유형 | 사용 기준 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 포맷팅, 세미콜론 등 코드 동작에 영향이 없는 변경. CSS 변경에도 사용 |
| `refactor` | 기능 변경 없이 코드 구조 개선 |
| `test` | 테스트 코드 또는 리팩토링 테스트 코드 추가·수정 |
| `chore` | 패키지 설정, `.gitignore` 등 기타 관리 작업 및 오타 수정 |
| `design` | 사용자 UI 디자인 변경 |
| `comment` | 주석 추가 또는 수정 |
| `rename` | 파일 또는 폴더 이름 변경·이동만 수행 |
| `remove` | 파일 삭제만 수행 |
| `!BREAKING CHANGE` | 호환성을 깨는 큰 API 변경 |
| `!HOTFIX` | 긴급하게 치명적 버그 수정 |

## 작성 원칙

- 한 커밋에는 한 가지 문제나 변경 목적만 담습니다.
- 커밋 메시지는 팀원과의 소통과 변경 이력 추적에 도움이 되도록 구체적으로 작성합니다.
- CSS 변경에는 `design`이 아니라 `style`을 사용합니다.
- 여러 줄 메시지는 제목과 본문을 빈 줄로 구분합니다.

```bash
git commit -m "feat: 회원가입 기능 추가

- 회원가입 입력 검증 구현"
```
